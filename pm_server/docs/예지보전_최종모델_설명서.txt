예지보전 최종 모델 설명서 (수위계·전광판)
============================================================
이 문서는 예지보전_최종모델_v1.zip(pm_final 폴더)이 무엇이고, 어떻게 쓰고, 앞으로 어떻게 붙일지를 한 곳에 적은 것이다.
자세한 사용법·검증 숫자는 zip 안의 pm_final/README.md 에 있다.

1. 한 줄 요약
------------------------------------------------------------
수위계와 전광판 모델을 "점수 0~100 + 근거 문장"이 바로 나오게 다시 학습해서 코드와 함께 묶은 것이다.
함수 하나(diagnose)를 부르면 risk_score, risk_level, reasons[] 가 나온다.
합성 데이터로 학습한 시연·개발용이다. 실제 데이터가 쌓이면 같은 스크립트로 다시 학습한다.

2. 이 zip 의 구성
------------------------------------------------------------
pm_final/
  pdm_common.py     점수 눈금(0~100), 등급(정상/주의/위험), 연속 조건      <- 서버에 필요
  pdm_wl.py         수위계: 특징 계산, diagnose(), 학습                    <- 서버에 필요
  pdm_vms.py        전광판: 특징 계산, diagnose(), build_baseline(), 학습  <- 서버에 필요
  models/
    wl_model.joblib   수위계 모델 번들                                      <- 서버에 필요
    vms_model.joblib  전광판 모델 번들                                      <- 서버에 필요
  bench_common.py   학습할 때만 쓴다 (서버에는 필요 없음)
  verify.py         점수 눈금·서비스 함수 일치 검증
  make_examples.py  예시 파일 만들기
  examples/         입력 CSV, 출력 JSON 예시
  verify_result.json 검증 결과 숫자
  requirements.txt  라이브러리 버전 (모델을 만든 버전 그대로)
  README.md         상세 설명
  예지보전_모델_전달사항_팀원용.txt  CCTV·배수펌프 모델을 만들 때 맞춰야 할 규칙

주의: 모델 파일(.joblib)만 넘기면 안 된다. 특징 계산과 근거 문장을 만드는 코드가 pdm_*.py 에 있어서
pdm_common.py, pdm_wl.py, pdm_vms.py, models/ 를 같이 넘겨야 한다.
라이브러리 버전이 requirements.txt 와 같아야 모델 파일이 안전하게 불러와진다.

3. 두 모델의 내용
------------------------------------------------------------
[수위계] 센서 이상 탐지 (침수 위험 예측이 아니라 "수위계가 고장·오작동인지" 보는 모델)
  - 조합: 추세 제거 잔차 특징 5개 + IsolationForest, 센서 7개가 공용 모델 1개를 쓴다.
  - 입력: 센서 1개의 5분 간격 수위(level_m), 최근 2~3일(최소 300개).
  - 특징 5개: res_max3, res_max12, res_sd12, slope_dev, slope24
    (직전 6시간 중앙값을 뺀 잔차와 기울기를, 센서 자신의 평소 변동폭으로 나눈 값)
  - 연속 2번(10분) 넘어야 높은 점수가 된다.
  - 주의: 수위계 고착(값이 멈춤)은 멈춰 있는 동안이 아니라 풀리는 순간에 잡힌다.
    멈춤 자체는 "같은 값이 N번 연속" 규칙으로 따로 잡는 것을 권장한다. 끊김(dropout)도 규칙으로 처리한다.
  - 5분 간격은 가정이다. 실제 수위계 데이터가 시간별이면 특징의 창 길이를 바꿔 다시 학습해야 한다.

[전광판] 고장 전조 탐지
  - 조합: 유형별 대표 5변수(평소 대비 편차) + GMM, 장비 60대가 공용 모델 1개를 쓴다. 다른 장비와 비교하지 않는다.
  - 입력: 장비 1대의 1시간 간격 센서값, 최근 72시간 + 하루 한 번 만든 "평소 값".
  - 센서 6컬럼: temperature_c, ambient_c, ripple_v, response_time_ms, error_count, bad_pixel_pct
    (본체-외기 온도차를 만들어 5변수로 쓴다: 열 / 전원 / 통신 2개 / 화면)
  - 평소 값: 그 장비의 7일 전까지의 30일 이력으로 만든다. build_baseline() 으로 하루 한 번 만들어 저장해 두고
    diagnose(..., baseline=...) 에 넘긴다. 새 장비는 10일치가 쌓일 때까지 baseline_pending.
  - 연속 3번(3시간) 넘어야 높은 점수가 된다. 의심 원인(suspected_cause): power / comm / thermal / display.

4. 출력 (두 모델 공통 형태)
------------------------------------------------------------
  risk_score   0~100 (고장 확률이 아니라 "평소와 다른 정도 = 점검 후보")
  risk_level   정상 0~39 / 주의 40~69 / 위험 70+  (Spring 의 pm_threshold 기준과 같다)
  reasons[]    항목, 센서, 현재, 평소, 설명, 영향도  (평소 범위 안이면 나오지 않는다)
  status       ok / insufficient_history / insufficient_data / stale / baseline_pending
  warnings     중복 제거, 범위 밖 값 처리 같은 안내
  (수위계) anomaly_type   (전광판) suspected_cause
점수를 낼 수 없을 때(데이터 부족 등)는 점수를 억지로 만들지 않고 status 로 알려준다.

5. 검증 결과 (합성 데이터, 학습에 안 쓴 시험 기간)
------------------------------------------------------------
                                   수위계              전광판
  정상 구간 40점 이상 / 70점 이상    2.5% / 0.05%       2.6% / 0.2%
  고장 사건 중 70점 이상             91% (58건)         96% (47건)
  헛알림                             센서·월 0.93건     장비·월 0.26건
  중앙 탐지                          시작 후 5분         고장 5.7일 전
고장 모양을 직접 설계한 합성 데이터라 수치는 낙관적이다. 참고치로만 본다.

6. 내가 하려는 구조 (역할 분담)
------------------------------------------------------------
  Spring  : 센서 데이터를 읽어온다. 센서 stub(시연용 가짜 센서값)도 Spring 에서 만든다.
            점수·근거 저장, 등급 판정(pm_threshold), 대시보드·알림은 기존대로 Spring.
  FastAPI : Spring 이 보낸 센서 데이터로 점수와 근거를 계산해서 돌려준다.
            수위계·전광판은 이 zip 의 diagnose() 를 쓰고, CCTV·배수펌프는 팀원 모델을 같은 형태로 붙인다.
  즉 FastAPI 는 데이터를 직접 읽지 않고, Spring 이 보내준 데이터만 계산한다. (서버는 요청을 기억하지 않는다.)

7. 아직 정해지지 않은 것 (나중에 정리해서 전달)
------------------------------------------------------------
  - 장비 조회 API 는 지금도 있지만, DB 를 바꾸는 작업이 진행 중이다.
    그래서 FastAPI 와 Spring 사이의 계약(요청·응답 형식, 필드 이름, 장비 목록 조회 방식 등)은 DB 정리가 끝난 뒤
    내가 따로 정리해서 줄 것이다. 그 전에는 계약을 추측해서 만들지 않는다.
  - 그때까지는 이 zip 의 diagnose() 입출력(위 3~4장)을 기준으로 FastAPI 쪽 로직만 준비해 둔다.
  - 전광판 평소 값(baseline)을 어디에 저장하고 누가 하루 한 번 만들지(Spring 스케줄러 / FastAPI) 는 계약과 함께 정한다.
  - 수위계 실제 데이터 간격(5분인지 시간별인지)에 따라 모델 재학습이 필요할 수 있다.

8. 팀원이 해야 할 일
------------------------------------------------------------
  - CCTV·배수펌프 모델은 같은 형태(risk_score 0~100, risk_level, reasons[])로 나오게 만든다.
    맞춰야 할 규칙은 예지보전_모델_전달사항_팀원용.txt 를 따른다.
  - 위 7장의 계약이 오기 전까지는 FastAPI 엔드포인트의 요청·응답 형식을 확정하지 않는다.
  - 서버에는 pdm_common.py / pdm_wl.py / pdm_vms.py / models/ 와 requirements.txt 의 버전을 그대로 쓴다.
