# 예지보전 최종 모델 (수위계·전광판)

벤치마크에서 가장 잘 나온 조합을 **0~100점 + 사유 문장**이 바로 나오게 다시 학습한 것이에요.

| 대상 | 조합 | 입력 | 모델 파일 |
|---|---|---|---|
| 수위계 | 추세 제거 잔차 5개 + IsolationForest | 5분 간격 수위, 센서별 | `models/wl_model.joblib` |
| 전광판 | 유형별 대표 5변수(평소 대비 편차) + GMM | 1시간 간격 센서값, 장비별 | `models/vms_model.joblib` |

합성 데이터(`합성데이터_v4`)로 학습한 **시연·개발용**이에요. 실제 데이터가 쌓이면 같은 스크립트로 다시 학습해요.

## 폴더
```
pdm_common.py   점수 눈금(0~100), 등급, 연속 조건
pdm_wl.py       수위계: 특징 계산 · diagnose() · 학습
pdm_vms.py      전광판: 특징 계산 · diagnose() · build_baseline() · 학습
bench_common.py 학습할 때만 씀 (서버에는 필요 없어요)
verify.py       점수 눈금 검증, make_examples.py 예시 만들기
models/         학습된 번들 2개   examples/ 입력·출력 예시   verify_result.json 검증 결과
```
서버에서는 `pdm_common.py` + `pdm_wl.py`/`pdm_vms.py` + `models/` 만 있으면 돼요. 라이브러리 버전은 `requirements.txt` (모델을 만든 버전 그대로).

## 사용법
```python
import pdm_wl, pdm_vms
bw = pdm_wl.load_bundle("models/wl_model.joblib")
r = pdm_wl.diagnose(bw, "S2", df)            # df: observed_at, level_m (5분 간격, 최근 2~3일)

bv = pdm_vms.load_bundle("models/vms_model.joblib")
base = pdm_vms.build_baseline(history_df)    # 하루 한 번: 장비 최근 37일 이력 -> 오늘의 평소 값
r = pdm_vms.diagnose(bv, "VMS-011", df72, baseline=base)   # df72: 최근 72시간
```
반환 키: `risk_score(0~100)`, `risk_level(정상 0~39 · 주의 40~69 · 위험 70+)`, `reasons[]`(항목·센서·현재·평소·설명·영향도), `status`, `warnings`, 그리고 수위계 `anomaly_type` / 전광판 `suspected_cause`(power·comm·thermal·display).
입력·출력 예시는 `examples/` 를 보세요.

`status`: `ok` · `insufficient_history`(데이터 부족) · `insufficient_data`(최근 값이 비어 있음) · `stale`(최신 시각이 너무 오래됨, `now=` 를 넘겼을 때) · `baseline_pending`(전광판: 평소 값 없음). 점수를 못 낼 때는 점수를 억지로 만들지 않아요. 중복 시각은 지우고, 범위 밖 값은 빈 값으로 바꾸고(채우지 않음) `warnings` 에 알려요.

## 점수가 어떻게 0~100이 되나
모델이 내는 값(이상 점수)을 검증 구간(정상만)의 분포로 구간별 직선으로 바꿔요.

| 점수 | 기준 |
|---|---|
| 0 | 정상 점수의 1% 지점 |
| 20 | 정상 중앙값 |
| 40 | 정상 99% 지점 (단, 70점 기준과 너무 붙지 않게 제한) |
| 70 | **알림 기준**: 검증 구간에서 헛알림 묶음이 예산 이하가 되는 가장 낮은 임계값 |
| 100 | 70점 기준 + (70점 기준 - 중앙값) |

* 70 이상이 되려면 **연속으로** 넘어야 해요 (수위계 2번=10분, 전광판 3번=3시간). 마지막 n개 점수의 최솟값을 점수로 쓰는 방식이에요.
* 눈금 숫자(p01·p50·p99·알림 기준)는 번들 `anchors` 안에 있어요. 점수는 고장 확률이 아니라 "평소와 다른 정도(점검 후보)"예요.

## 시험 구간 검증 (합성 데이터, 처음 보는 기간)
| | 수위계 | 전광판 |
|---|---|---|
| 정상 구간에서 점수 40 이상 / 70 이상 | 2.5% / 0.05% | 2.6% / 0.2% |
| 고장 사건 중 70점 이상이 된 것 | 91% (58건) | 96% (47건) |
| 헛알림 | 센서·월 0.93건 | 장비·월 0.26건 |
| 중앙 탐지 | 시작 후 5분 | 고장 5.7일 전 |
| 70점 이상: 정상 상승·폭염 구간 | 2.0% | 3.3% |

유형별 70점 이상 비율: 수위계 스텝 100 · 스파이크 100 · 고착 100(아래 주의) · 드리프트 86 · 노이즈 69 / 전광판 열 100 · 화면 100 · 통신 92 · 전원 91.
전체 숫자는 `verify_result.json`.

## 꼭 알아둘 점
1. **입력 규격이 지금 통합 서버(`wl_ai_server`·`vms_ai_server`)와 달라요.** 통합 서버 쪽 수정이 필요해요.
   * 수위계: 기존은 시간별 14일. 이 모델은 **5분 간격** 최근 2~3일(최소 300개). 실제 수위계가 시간별이면 특징 창을 시간별에 맞게 바꿔 다시 학습해야 해요.
   * 전광판: 기존은 최근 72시간·센서 6종·전체 장비 한꺼번에. 이 모델은 장비 1대씩, 센서 6컬럼(`temperature_c, ambient_c, ripple_v, response_time_ms, error_count, bad_pixel_pct`) + 하루 한 번 만든 평소 값. 다른 장비와 비교하지 않아요.
2. **수위계 고착(값이 멈춤)은 멈춰 있는 동안이 아니라 풀리는 순간에 잡혀요** (멈춘 구간 중 70점 이상 0%). 멈춤 자체는 규칙(같은 값이 N번 연속)으로 따로 잡는 걸 권장해요. 끊김(dropout)도 규칙이에요.
3. 전광판 평소 값은 **7일 전까지의 30일**로 만들어요 (열화가 평소에 섞이는 걸 막으려고). 새 장비는 10일치가 쌓일 때까지 `baseline_pending` 이에요. 번들 안의 평소 값은 임시값이에요.
4. 알림 기준(70점) 예산: 수위계는 검증 구간에서 센서·월 1건. 전광판은 처음 0.25건으로 했더니 시험에서 고장의 51%만 잡았어요(검증 구간이 시험보다 헛알림이 많은 구간이라 기준이 너무 높게 잡힘). **시험 결과를 본 뒤 장비·월 1건으로 올렸어요.** 아래 표처럼 기준에 따라 달라지니 운영에서 다시 정하세요.

   | 전광판 검증 예산(장비·월) | 시험 재현율 | 시험 헛알림(장비·월) | 중앙 선행 |
   |---|---|---|---|
   | 0.25 | 51% | 0.00 | 2.7일 |
   | 0.5 | 68% | 0.02 | 3.2일 |
   | 0.75 | 94% | 0.19 | 5.2일 |
   | **1.0 (사용)** | 96% | 0.26 | 5.7일 |
   | 1.5 | 96% | 0.65 | 6.8일 |

5. 사유(`reasons`)는 특징값의 평소 대비 편차가 큰 순서 상위 3개예요 (평소 범위 안이면 안 나와요).
6. 고장 모양을 내가 설계한 합성 데이터라 수치는 낙관적이에요. 실제 데이터로 재학습·재검증 전까지 참고치로만 보세요.

## 다시 학습
```bash
python pdm_wl.py train  --data <wl 합성데이터 폴더>  --out models/wl_model.joblib
python pdm_vms.py train --data <vms 합성데이터 폴더> --out models/vms_model.joblib
python verify.py
```
